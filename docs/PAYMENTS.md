# المدفوعات

**الحالة:** مخطط. لا كود دفع قبل المرحلة 4، والبداية بالبيئات التجريبية فقط. تفعيل الإنتاج يحتاج موافقة مستقلة من المالك.

**تنبيه تحقق:** حقائق Moyasar أدناه مأخوذة من ملخصات بحث لوثائقه الرسمية، لأن `docs.moyasar.com` لم يكن متاحًا للقراءة المباشرة من جلسة التخطيط. **تُعاد قراءتها من المصدر مباشرة قبل المرحلة 4**، وكذلك وثائق Tabby وTamara. يلزم السماح بنطاقات الوثائق الثلاثة في إعدادات شبكة الجلسة.

**مفتاح التصنيف:** `[حقيقة]` · `[متطلب]` · `[توصية]` · `[افتراض]` · `[خارجي]` · `[لاحقًا]`.

## 1. واجهة المزوّد الموحدة `[توصية]`

وحدة تنسيق واحدة، ومحوّل لكل مزوّد يطبّق نفس الواجهة:

| العملية         | الوصف                                                    |
| --------------- | -------------------------------------------------------- |
| `createSession` | إنشاء جلسة أو دفعة بمبلغ الطلب ومرجعه ومفتاح عدم التكرار |
| `fetchStatus`   | قراءة الحالة المعتمدة من المزوّد نفسه                    |
| `capture`       | تحصيل دفعة مفوَّضة (حيث ينطبق)                           |
| `refund`        | استرداد كلي أو جزئي                                      |
| `verifyWebhook` | التحقق من مصدر الإشعار قبل قراءة محتواه                  |
| `mapStatus`     | تحويل حالة المزوّد إلى آلة الحالة الداخلية               |

المحوّلات لا تعرف شيئًا عن الاشتراكات؛ التفعيل في وحدة الطلبات. لا اختراع لنقاط نهاية أو حقول: كل حقل يُؤخذ من الوثيقة الرسمية ويُذكر رابطه في الكود.

## 2. الحقائق المتحقق منها

### Moyasar (مدى، فيزا، ماستركارد، Apple Pay)

| الحقيقة                                                                 | المصدر                                                                                                                                |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| المبلغ بأصغر وحدة (هللة)، أعداد صحيحة                                   | [Create Payment](https://docs.moyasar.com/api/payments/01-create-payment)                                                             |
| `given_id` (UUID) مفتاح عدم التكرار؛ إعادة استعماله لدفعة أخرى ترجع خطأ | [Idempotency](https://docs.moyasar.com/api/idempotency)                                                                               |
| المصادقة Basic بالمفتاح السري                                           | وثائق الواجهة                                                                                                                         |
| الإشعار يحمل `secret_token` يُقارَن على الخادم؛ الرابط HTTPS            | [Webhook Reference](https://docs.moyasar.com/webhook-reference) · [Setting up Webhooks](https://docs.moyasar.com/setting-up-webhooks) |
| أحداث مثل `payment_paid` و`payment_refunded`                            | نفس المرجع                                                                                                                            |
| شهادات Apple Pay تُضبط من لوحة Moyasar                                  | [Apple Pay](https://docs.moyasar.com/apple-pay-payment)                                                                               |

الأثر: `secret_token` أضعف من توقيع على الجسم، لذلك **نقرأ الدفعة من واجهة Moyasar دائمًا قبل أي تفعيل**. لم تتأكد القائمة الكاملة لقيم الحالة (مثل `authorized` و`refunded`)؛ تؤخذ من مرجع كائن الدفعة قبل التنفيذ. مصدر خارجي ذكر توقيع HMAC؛ وثائق Moyasar نفسها تصف `secret_token`، والحسم بقراءة المصدر.

### Tabby (تقسيط)

| الحقيقة                                                                                   | المصدر                                                                                     |
| ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| الحالات: `CREATED` ← `AUTHORIZED` ← `CLOSED`؛ `REJECTED` و`EXPIRED` نهائيتان              | [Payment Statuses](https://docs.tabby.ai/pay-in-4-custom-integration/payment-statuses)     |
| التحصيل من `AUTHORIZED` فقط؛ التحصيل الكامل يحوّلها `CLOSED`، والجزئي يبقيها `AUTHORIZED` | [Payment Processing](https://docs.tabby.ai/pay-in-4-custom-integration/payment-processing) |
| حالات الإشعار بأحرف صغيرة، وحالات القراءة بأحرف كبيرة                                     | [Webhooks](https://docs.tabby.ai/pay-in-4-custom-integration/webhooks)                     |
| إشعار الإغلاق قد يسبق التفويض                                                             | نفس المرجع                                                                                 |

الأثر: الحالة تتقدم فقط، وحدث `authorized` متأخر لا يكتب فوق `closed`.

### Tamara (تقسيط)

| الحقيقة                                                                           | المصدر                                                                             |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| بعد إشعار `approved` يستدعي الخادم `POST /orders/{order_id}/authorise` ثم التحصيل | [Direct Online Checkout](https://docs.tamara.co/docs/direct-online-checkout)       |
| رمز الإشعار JWT بـHS256، يصل في `tamaraToken` وفي ترويسة `Authorization`          | [Webhook Subscription](https://docs.tamara.co/docs/webhook-subscription)           |
| رمز الإشعار غير رمز الواجهة                                                       | [Transaction Authorisation](https://docs.tamara.co/docs/transaction-authorisation) |

الأثر: مفتاحان منفصلان في الإعدادات، ولا يُستعمل أحدهما مكان الآخر.

`[حقيقة]` الـCRM يطبّق اليوم ربط Tabby وTamara المباشر بهذا النمط نفسه (`inc/tabby.php`، `inc/tamara.php` في `masterway-crm`)، وهو مرجع سلوك مجرَّب، لا كود يُنقل.

## 3. قواعد لا استثناء فيها `[متطلب]`

1. لا تفعيل اشتراك من إعادة توجيه المتصفح ولا من رد ناجح في الواجهة.
2. قبل التفعيل تُطابَق من المزوّد: الحالة، التاجر، مرجع الطلب، العملة، المبلغ.
3. كل طلب مدفوع يفعّل اشتراكه مرة واحدة فقط (قيد فريد + قفل صف).
4. لا بيانات بطاقة خام ولا CVV عندنا؛ حقول المزوّد المستضافة أو المرمّزة فقط.
5. كل محاولة دفع بمعرّف فريد ومفتاح عدم تكرار.
6. الإشعار يُوثَّق مصدره، يُسجَّل، ويُرفض تكراره، ثم تُقرأ الحالة من المزوّد.
7. مهمة مطابقة دورية للطلبات المعلّقة (الإشعار قد لا يصل).
8. وسيلة الدفع تُعرض فقط إن كانت متاحة ومناسبة؛ التقسيط «حسب موافقة المزوّد» بلا وعد.
9. فصل تام بين مفاتيح التجربة والإنتاج؛ لا مفتاح في git ولا في المحادثة.
10. سجلات دفع منظَّمة بلا بيانات حساسة.

## 4. خطر التعارض مع الـCRM

`[حقيقة]` الـCRM ينشئ اليوم جلسات Tabby وTamara عبر الواتساب، غالبًا على نفس حساب التاجر.

| الخطر                                | المعالجة                                            |
| ------------------------------------ | --------------------------------------------------- |
| إشعار طلب المنصة يصل للـCRM أو العكس | بادئة مميزة لمراجع المنصة؛ كل نظام يتجاهل ما ليس له |
| رابط إشعار واحد مسجّل للتاجر         | يُتحقق من كل مزوّد: هل يقبل أكثر من رابط؟ `[خارجي]` |
| بيعة مسجّلة مرتين                    | مطابقة يومية بين طلبات المنصة وسجل `sales`          |

`[لاحقًا]` الـCRM يطلب روابط الدفع من المنصة فيصير المنسّق واحدًا.

## 5. حالات الاختبار الخمس عشرة `[متطلب]`

تنجح كلها في البيئة التجريبية قبل إعلان المرحلة 4 منتهية:

| #   | الحالة               | النتيجة المتوقعة                      |
| --- | -------------------- | ------------------------------------- |
| 1   | شراء ناجح            | طلب `paid`، اشتراك واحد، حدث للـCRM   |
| 2   | دفع فاشل             | لا تفعيل، سبب واضح وبدائل             |
| 3   | دفع ملغى من العميل   | لا تفعيل، المدخلات محفوظة             |
| 4   | دفع معلّق            | صفحة «نتحقق»، والمطابقة تحسمه         |
| 5   | إشعار مكرر           | يُرفض الثاني، لا أثر مزدوج            |
| 6   | إشعار بترتيب معكوس   | الحالة لا تتراجع                      |
| 7   | مبلغ لا يطابق        | لا تفعيل، تنبيه للإدارة               |
| 8   | طلب إداري بلا صلاحية | يُرفض ويُسجَّل                        |
| 9   | عرض منتهٍ            | لا يُطبَّق، والسعر يُعاد حسابه        |
| 10  | كوبون غير صالح       | رسالة واضحة، لا خصم                   |
| 11  | منع الشراء المزدوج   | ضغطتان = طلب واحد                     |
| 12  | تفعيل الاشتراك       | مرة واحدة بالتواريخ الصحيحة           |
| 13  | استرداد              | آلة حالة الاسترداد، وحدث `refund`     |
| 14  | تجديد                | تمديد صحيح، وحدث `membership_renewed` |
| 15  | استرجاع دفع منقطع    | يكتمل من الإشعار أو المطابقة          |

## 7. غير محسوم — قرار المالك

- التحصيل فوري عند التفويض أم مؤجل؟ (يتبع قاعدة بدء الاشتراك)
- سياسة الاسترداد وأهليته، ومن يوافق عليه في لوحة الإدارة.
- هل تبقى روابط الدفع عبر الواتساب في الـCRM كما هي بعد إطلاق المنصة؟
