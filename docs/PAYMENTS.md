# المدفوعات

**الحالة:** مخطط. لا كود دفع قبل المرحلة 4، والبداية بالبيئات التجريبية فقط. تفعيل الإنتاج يحتاج موافقة مستقلة من المالك. المرحلة 3 سلّمت نقطة التسليم (`markOrderPaid`) بلا أي مزوّد؛ عقدها وشروطها الصلبة في القسم 8.

**تنبيه تحقق:** حقائق Moyasar أدناه مأخوذة من ملخصات بحث لوثائقه الرسمية، لأن `docs.moyasar.com` لم يكن متاحًا للقراءة المباشرة من جلسة التخطيط. **تُعاد قراءتها من المصدر مباشرة قبل المرحلة 4**، وكذلك وثائق Tabby وTamara. يلزم السماح بنطاقات الوثائق الثلاثة في إعدادات شبكة الجلسة.

**مفتاح التصنيف:** `[حقيقة]` · `[متطلب]` · `[توصية]` · `[افتراض]` · `[خارجي]` · `[لاحقًا]`.

## 1. واجهة المزوّد الموحدة `[توصية]`

وحدة تنسيق واحدة، ومحوّل لكل مزوّد يطبّق نفس الواجهة:

| العملية         | الوصف                                                    |
| --------------- | -------------------------------------------------------- |
| `createSession` | إنشاء جلسة أو دفعة بمبلغ الطلب ومرجعه ومفتاح عدم التكرار |
| `fetchStatus`   | قراءة الحالة المعتمدة من المزوّد نفسه                    |
| `capture`       | تحصيل دفعة مفوَّضة (حيث ينطبق)                           |
| `refund`        | استرداد كلي أو جزئي                                      |
| `verifyWebhook` | التحقق من مصدر الإشعار قبل قراءة محتواه                  |
| `mapStatus`     | تحويل حالة المزوّد إلى آلة الحالة الداخلية               |

المحوّلات لا تعرف شيئًا عن الاشتراكات؛ التفعيل في وحدة الطلبات. لا اختراع لنقاط نهاية أو حقول: كل حقل يُؤخذ من الوثيقة الرسمية ويُذكر رابطه في الكود.

| الحقيقة                                                                 | المصدر                                                                                                                                |

## 3. قواعد لا استثناء فيها `[متطلب]`

1. لا تفعيل اشتراك من إعادة توجيه المتصفح ولا من رد ناجح في الواجهة.
2. قبل التفعيل تُطابَق من المزوّد: الحالة، التاجر، مرجع الطلب، العملة، المبلغ.
3. كل طلب مدفوع يفعّل اشتراكه مرة واحدة فقط (قيد فريد + قفل صف).
4. لا بيانات بطاقة خام ولا CVV عندنا؛ حقول المزوّد المستضافة أو المرمّزة فقط.
5. كل محاولة دفع بمعرّف فريد ومفتاح عدم تكرار.
6. الإشعار يُوثَّق مصدره، يُسجَّل، ويُرفض تكراره، ثم تُقرأ الحالة من المزوّد.
7. مهمة مطابقة دورية للطلبات المعلّقة (الإشعار قد لا يصل).
8. وسيلة الدفع تُعرض فقط إن كانت متاحة ومناسبة؛ التقسيط «حسب موافقة المزوّد» بلا وعد.
9. فصل تام بين مفاتيح التجربة والإنتاج؛ لا مفتاح في git ولا في المحادثة.
10. سجلات دفع منظَّمة بلا بيانات حساسة.

## 4. خطر التعارض مع الـCRM

`[حقيقة]` الـCRM ينشئ اليوم جلسات Tabby وTamara عبر الواتساب، غالبًا على نفس حساب التاجر.

| الخطر                                | المعالجة                                            |
| ------------------------------------ | --------------------------------------------------- |
| إشعار طلب المنصة يصل للـCRM أو العكس | بادئة مميزة لمراجع المنصة؛ كل نظام يتجاهل ما ليس له |
| رابط إشعار واحد مسجّل للتاجر         | يُتحقق من كل مزوّد: هل يقبل أكثر من رابط؟ `[خارجي]` |
| بيعة مسجّلة مرتين                    | مطابقة يومية بين طلبات المنصة وسجل `sales`          |

`[لاحقًا]` الـCRM يطلب روابط الدفع من المنصة فيصير المنسّق واحدًا.

## 7. غير محسوم — قرار المالك

- التحصيل فوري عند التفويض أم مؤجل؟ (يتبع قاعدة بدء الاشتراك)
- سياسة الاسترداد وأهليته، ومن يوافق عليه في لوحة الإدارة.
- هل تبقى روابط الدفع عبر الواتساب في الـCRM كما هي بعد إطلاق المنصة؟

## 8. عقد التسليم من المرحلة 3 `[متطلب]`

المرحلة 3 بنت الطلب المعلّق والتسوية بلا مزوّد. المرحلة 4 تكتب المحوّل والمطابقة، ولا تلمس منطق الطلب: تستدعي نقطة واحدة.

### التوقيع

```ts
// packages/domain — دفعة قُرئت حالتها من المزوّد نفسه، بقيمها الخام
interface VerifiedPayment {
  provider: string; // ^[a-z][a-z0-9_]{1,31}$ مثل "moyasar"
  providerPaymentId: string; // 1..200 محرف
  amountMinor: number; // بالهللة، عدد صحيح
  currency: string; // "SAR"
}

// packages/db — معاملة واحدة، لا استدعاء خارجي داخلها
markOrderPaid(db, {
  orderId: string,
  payment: VerifiedPayment,
  actor: "provider" | "system",
  now: Date,
}): Promise<Result<PaidOrder, DomainError>>

interface PaidOrder {
  orderId: string;
  reference: string; // MSR-NNNNNNN
  status: "paid" | "fulfilled" | "partially_refunded" | "refunded";
  membershipId: string | null;
  replayed: boolean; // الدفعة نفسها مسجّلة من قبل: لا كتابة
}
```

### النتائج

| النتيجة                                                  | المعنى                                                                              | ما يكتبه                                                    |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `ok`، `replayed: false`، `fulfilled`                     | سُجّلت الدفعة وأُنشئ الاشتراك (أو بلا اشتراك لطلب بلا سطر اشتراك) وسُلّم الطلب      | `paid_*`، صف `memberships`، تدقيق `payment_verified` وغيره  |
| `ok`، `replayed: false`، `paid`                          | طلب فيه برنامج رقمي: يبقى `paid` حتى يُحسم التسليم                                  | `paid_*` وتدقيقها                                           |
| `ok`، `replayed: true`                                   | المزوّد أعاد إرسال دفعة مسجّلة. الحالة الفعلية تُرجَع كما هي، ومنها حالتا الاسترداد | لا شيء                                                      |
| `validation payment.invalid_reference`                   | مزوّد أو معرّف بصيغة خاطئة                                                          | سطر `payment_rejected`                                      |
| `conflict order.already_paid`                            | دفعة أخرى على طلب مدفوع                                                             | سطر `payment_rejected`                                      |
| `conflict order.not_payable`                             | الطلب منتهٍ أو ملغى. **لا تفعيل**                                                   | سطر `payment_rejected` فيه المزوّد والمعرّف والمبلغ والعملة |
| `conflict payment.currency_mismatch` / `amount_mismatch` | العملة أو المبلغ بالهللة لا يطابق إجمالي الطلب                                      | سطر `payment_rejected`                                      |
| `conflict payment.already_used`                          | الدفعة نفسها مسجّلة على طلب آخر                                                     | سطر `payment_rejected`                                      |
| `not_found order.not_found`                              | لا طلب بهذا المعرّف                                                                 | لا شيء                                                      |

الرفض يُكتب في التدقيق ثم يُعتمد، فلا تضيع دفعة وصلت ولم تُسجَّل. أخطاء `invariant` أعطال تُصلَح، لا نتائج عمل.

### الضمانات في القاعدة

- مرة واحدة لكل طلب: قفل صف الطلب `FOR UPDATE`، والانتقال مشروط بـ`status = 'pending_payment'` ويجب أن يمسّ صفًا واحدًا، و`UNIQUE(memberships.order_id)` و`UNIQUE(memberships.order_item_id)`.
- الدفعة لا تُسجَّل مرتين: `UNIQUE(paid_provider, paid_provider_payment_id)`، ويُحوَّل خرقه إلى `payment.already_used`.
- المبلغ والعملة: CHECK `orders_payment_matches` (`paid_amount_minor = total_minor` و`paid_currency = currency`) و`orders_payment_complete`.
- `paid_*` لا تتغير بعد كتابتها، والطلب المنتهي أو الملغى أو المسترد نهائي، ولا عودة إلى `pending_payment` (trigger `orders_guard_update`).
- لا اشتراك لطلب غير مدفوع (مفتاح أجنبي مركّب على `(order_id, order_paid_at)`)، ولا اشتراكان متراكبان لعميل واحد: قفل صف العميل يسلسل فحص الاشتراك الحي، والثاني `scheduled` بلا تواريخ.

### شروط صلبة على المرحلة 4 قبل أي دفع حي

1. جلسة المزوّد أو رابط الدفع تنتهي قبل `orders.expires_at` بهامش يُحدَّد في المرحلة 4.
2. `expireDueOrders` يستثني كل طلب له محاولة دفع `pending` أو `authorized` (جدول `payment_attempts` في المرحلة 4).
3. `markOrderPaid` لا تُستدعى إلا بعد قراءة الحالة من المزوّد نفسه ومطابقة التاجر والمرجع `MSR` والمبلغ والعملة. لا من إعادة توجيه المتصفح ولا من جسم إشعار لم يُقرأ مقابله.
4. `order.not_payable` ينبّه الإدارة، ومعالجة الدفعة (استرداد أم تفعيل يدوي) قرار مالك.
5. التحقق من الجوال برمز قبل فتح العلم للعموم. حدود المحاولات الحالية (القرار 42) تبطئ السكربت ولا تمنع من يكتب جوال غيره.
6. جدولة `pnpm --filter @masar/db orders:expire` (مؤقت systemd أو cron) قبل فتح العلم، فلا تبقى طلبات فائتة تحجز كوبونًا محدودًا (القرار 41).

### البادئة MSR

`[خارجي]` أرقام طلبات المنصة `MSR-` وسبعة أرقام. قبل المرحلة 4 يُتحقق من أنها لا تتعارض مع مراجع الـCRM عند Tabby وTamara (القسم 4)، ومن أن كل نظام يتجاهل إشعارات الآخر بها. حتى ذلك تُستعمل في الاختبار فقط.
