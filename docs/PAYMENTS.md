# المدفوعات

**الحالة:** أساس الدفع (المرحلة 4أ) مبني ومختبَر **بلا مفاتيح ولا اتصال بأي مزوّد**، ومغلق افتراضيًا: القسم 9 يصف ما بُني، والقسم 10 خطوات ربط Moyasar لاحقًا، والقسم 11 ما ينتظر تجربة البيئة التجريبية (WP0). لا دفع حي: `PAYMENTS_MODE=live` مرفوض في الكود حتى يأذن المالك إذنًا مستقلًا. التصميم الكامل وحقائق المزوّدين بروابطها في `PHASE4_PAYMENTS_DESIGN.md`.

**تنبيه تحقق:** جدول القسم 2 كُتب في التخطيط من ملخصات بحث وروابطه بصيغة قديمة. المرجع المعتمد الآن هو `PHASE4_PAYMENTS_DESIGN.md` §3 و§11 (قُرئت وثائق المزوّدين مباشرة في 2026-11-25)، ومحوّل Moyasar كُتب من تلك الصفحات نفسها وروابطها في رؤوس ملفاته. تأكد منها: الإشعار يحمل `secret_token` بلا توقيع HMAC، ورابط مرجع الإشعارات الحالي `docs.moyasar.com/docs/api/other/webhooks/webhook-reference.md`.

**مفتاح التصنيف:** `[حقيقة]` · `[متطلب]` · `[توصية]` · `[افتراض]` · `[خارجي]` · `[لاحقًا]`.

## 1. واجهة المزوّد الموحدة `[توصية]`

وحدة تنسيق واحدة، ومحوّل لكل مزوّد يطبّق نفس الواجهة:

| العملية         | الوصف                                                    |
| --------------- | -------------------------------------------------------- |
| `createSession` | إنشاء جلسة أو دفعة بمبلغ الطلب ومرجعه ومفتاح عدم التكرار |
| `fetchStatus`   | قراءة الحالة المعتمدة من المزوّد نفسه                    |
| `capture`       | تحصيل دفعة مفوَّضة (حيث ينطبق)                           |
| `refund`        | استرداد كلي أو جزئي                                      |
| `verifyWebhook` | التحقق من مصدر الإشعار قبل قراءة محتواه                  |
| `mapStatus`     | تحويل حالة المزوّد إلى آلة الحالة الداخلية               |

المحوّلات لا تعرف شيئًا عن الاشتراكات؛ التفعيل في وحدة الطلبات. لا اختراع لنقاط نهاية أو حقول: كل حقل يُؤخذ من الوثيقة الرسمية ويُذكر رابطه في الكود.

## 3. قواعد لا استثناء فيها `[متطلب]`

1. لا تفعيل اشتراك من إعادة توجيه المتصفح ولا من رد ناجح في الواجهة.
2. قبل التفعيل تُطابَق من المزوّد: الحالة، التاجر، مرجع الطلب، العملة، المبلغ.
3. كل طلب مدفوع يفعّل اشتراكه مرة واحدة فقط (قيد فريد + قفل صف).
4. لا بيانات بطاقة خام ولا CVV عندنا؛ حقول المزوّد المستضافة أو المرمّزة فقط.
5. كل محاولة دفع بمعرّف فريد ومفتاح عدم تكرار.
6. الإشعار يُوثَّق مصدره، يُسجَّل، ويُرفض تكراره، ثم تُقرأ الحالة من المزوّد.
7. مهمة مطابقة دورية للطلبات المعلّقة (الإشعار قد لا يصل).
8. وسيلة الدفع تُعرض فقط إن كانت متاحة ومناسبة؛ التقسيط «حسب موافقة المزوّد» بلا وعد.
9. فصل تام بين مفاتيح التجربة والإنتاج؛ لا مفتاح في git ولا في المحادثة.
10. سجلات دفع منظَّمة بلا بيانات حساسة.

## 4. خطر التعارض مع الـCRM

`[حقيقة]` الـCRM ينشئ اليوم جلسات Tabby وTamara عبر الواتساب، غالبًا على نفس حساب التاجر.

| الخطر                                | المعالجة                                            |
| ------------------------------------ | --------------------------------------------------- |
| إشعار طلب المنصة يصل للـCRM أو العكس | بادئة مميزة لمراجع المنصة؛ كل نظام يتجاهل ما ليس له |
| رابط إشعار واحد مسجّل للتاجر         | يُتحقق من كل مزوّد: هل يقبل أكثر من رابط؟ `[خارجي]` |
| بيعة مسجّلة مرتين                    | مطابقة يومية بين طلبات المنصة وسجل `sales`          |

`[لاحقًا]` الـCRM يطلب روابط الدفع من المنصة فيصير المنسّق واحدًا.

## 7. غير محسوم — قرار المالك

- التحصيل فوري عند التفويض أم مؤجل؟ (يتبع قاعدة بدء الاشتراك)
- سياسة الاسترداد وأهليته، ومن يوافق عليه في لوحة الإدارة.
- هل تبقى روابط الدفع عبر الواتساب في الـCRM كما هي بعد إطلاق المنصة؟

## 8. عقد التسليم من المرحلة 3 `[متطلب]`

المرحلة 3 بنت الطلب المعلّق والتسوية بلا مزوّد. المرحلة 4 تكتب المحوّل والمطابقة، ولا تلمس منطق الطلب: تستدعي نقطة واحدة.

### التوقيع

```ts
// packages/domain — دفعة قُرئت حالتها من المزوّد نفسه، بقيمها الخام
interface VerifiedPayment {
  provider: string; // ^[a-z][a-z0-9_]{1,31}$ مثل "moyasar"
  providerPaymentId: string; // 1..200 محرف
  amountMinor: number; // بالهللة، عدد صحيح
  currency: string; // "SAR"
}

// packages/db — معاملة واحدة، لا استدعاء خارجي داخلها
markOrderPaid(db, {
  orderId: string,
  payment: VerifiedPayment,
  actor: "provider" | "system",
  now: Date,
}): Promise<Result<PaidOrder, DomainError>>

interface PaidOrder {
  orderId: string;
  reference: string; // MSR-NNNNNNN
  status: "paid" | "fulfilled" | "partially_refunded" | "refunded";
  membershipId: string | null;
  replayed: boolean; // الدفعة نفسها مسجّلة من قبل: لا كتابة
}
```

### النتائج

| النتيجة                                                  | المعنى                                                                              | ما يكتبه                                                    |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `ok`، `replayed: false`، `fulfilled`                     | سُجّلت الدفعة وأُنشئ الاشتراك (أو بلا اشتراك لطلب بلا سطر اشتراك) وسُلّم الطلب      | `paid_*`، صف `memberships`، تدقيق `payment_verified` وغيره  |
| `ok`، `replayed: false`، `paid`                          | طلب فيه برنامج رقمي: يبقى `paid` حتى يُحسم التسليم                                  | `paid_*` وتدقيقها                                           |
| `ok`، `replayed: true`                                   | المزوّد أعاد إرسال دفعة مسجّلة. الحالة الفعلية تُرجَع كما هي، ومنها حالتا الاسترداد | لا شيء                                                      |
| `validation payment.invalid_reference`                   | مزوّد أو معرّف بصيغة خاطئة                                                          | سطر `payment_rejected`                                      |
| `conflict order.already_paid`                            | دفعة أخرى على طلب مدفوع                                                             | سطر `payment_rejected`                                      |
| `conflict order.not_payable`                             | الطلب منتهٍ أو ملغى. **لا تفعيل**                                                   | سطر `payment_rejected` فيه المزوّد والمعرّف والمبلغ والعملة |
| `conflict payment.currency_mismatch` / `amount_mismatch` | العملة أو المبلغ بالهللة لا يطابق إجمالي الطلب                                      | سطر `payment_rejected`                                      |
| `conflict payment.already_used`                          | الدفعة نفسها مسجّلة على طلب آخر                                                     | سطر `payment_rejected`                                      |
| `not_found order.not_found`                              | لا طلب بهذا المعرّف                                                                 | لا شيء                                                      |

الرفض يُكتب في التدقيق ثم يُعتمد، فلا تضيع دفعة وصلت ولم تُسجَّل. أخطاء `invariant` أعطال تُصلَح، لا نتائج عمل.

### الضمانات في القاعدة

- مرة واحدة لكل طلب: قفل صف الطلب `FOR UPDATE`، والانتقال مشروط بـ`status = 'pending_payment'` ويجب أن يمسّ صفًا واحدًا، و`UNIQUE(memberships.order_id)` و`UNIQUE(memberships.order_item_id)`.
- الدفعة لا تُسجَّل مرتين: `UNIQUE(paid_provider, paid_provider_payment_id)`، ويُحوَّل خرقه إلى `payment.already_used`.
- المبلغ والعملة: CHECK `orders_payment_matches` (`paid_amount_minor = total_minor` و`paid_currency = currency`) و`orders_payment_complete`.
- `paid_*` لا تتغير بعد كتابتها، والطلب المنتهي أو الملغى أو المسترد نهائي، ولا عودة إلى `pending_payment` (trigger `orders_guard_update`).
- لا اشتراك لطلب غير مدفوع (مفتاح أجنبي مركّب على `(order_id, order_paid_at)`)، ولا اشتراكان متراكبان لعميل واحد: قفل صف العميل يسلسل فحص الاشتراك الحي، والثاني `scheduled` بلا تواريخ.

### شروط صلبة على المرحلة 4 قبل أي دفع حي

1. جلسة المزوّد أو رابط الدفع تنتهي قبل `orders.expires_at` بهامش يُحدَّد في المرحلة 4.
2. `expireDueOrders` يستثني كل طلب له محاولة دفع `pending` أو `authorized` (جدول `payment_attempts` في المرحلة 4).
3. `markOrderPaid` لا تُستدعى إلا بعد قراءة الحالة من المزوّد نفسه ومطابقة التاجر والمرجع `MSR` والمبلغ والعملة. لا من إعادة توجيه المتصفح ولا من جسم إشعار لم يُقرأ مقابله.
4. `order.not_payable` ينبّه الإدارة، ومعالجة الدفعة (استرداد أم تفعيل يدوي) قرار مالك.
5. التحقق من الجوال برمز قبل فتح العلم للعموم. حدود المحاولات الحالية (القرار 42) تبطئ السكربت ولا تمنع من يكتب جوال غيره.
6. جدولة `pnpm --filter @masar/db orders:expire` (مؤقت systemd أو cron) قبل فتح العلم، فلا تبقى طلبات فائتة تحجز كوبونًا محدودًا (القرار 41).

### البادئة MSR

`[خارجي]` أرقام طلبات المنصة `MSR-` وسبعة أرقام. قبل المرحلة 4 يُتحقق من أنها لا تتعارض مع مراجع الـCRM عند Tabby وTamara (القسم 4)، ومن أن كل نظام يتجاهل إشعارات الآخر بها. حتى ذلك تُستعمل في الاختبار فقط.

## 9. ما بُني في المرحلة 4أ (بلا مفاتيح)

| الطبقة    | المكان                                                      | ما فيها                                                                                                                                                                                                       |
| --------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| المجال    | `packages/domain/src/payments`                              | آلة حالة المحاولة، `isLiveAttempt`، `paymentDeadline`، `decideVerification` (تسوية أو حادثة أو تجاهل)، أنواع الحوادث، `paymentDisplayState`                                                                   |

| المزوّدون | `packages/payments`                                         | المنفذ `PaymentProvider`، مزوّد الاختبار، محوّل Moyasar (فاتورة مستضافة)، `startPayment`، `syncAttempt`، `handlePaymentNotification`، `reconcileOnce`/`runReconcile`، والسكربت `payments:reconcile`           |
| الويب     | `apps/web/src/server/payments` وصفحاتها                     | زر «ادفع الآن»، صفحة العودة، `POST /api/payments/webhooks/[provider]`، وصفحة الدفع التجريبية لمزوّد الاختبار                                                                                                  |

**كيف تتحقق الشروط الصلبة (القسم 8):**

1. الجلسة تنتهي قبل المهلة: `deadline_at = expires_at − 5 دقائق` ويُرسل للمزوّد موعدًا للفاتورة، ولا تبدأ محاولة إن لم يبقَ `PAYMENTS_MIN_PAYMENT_MINUTES` قبله.
2. الإنهاء يستثني المحاولة الحيّة (`created` و`pending` و`authorized`، و`captured` بلا تسوية مسجّلة): جملتان في معاملة واحدة، والـtrigger T9 سدّ احتياطي. اختبار سباق بـ150 جولة.
3. `markOrderPaid` تُستدعى من مكان واحد، بعد قراءة الجلسة ودفعاتها من المزوّد بالمفتاح السري ومطابقة الجلسة ومعرّف المحاولة والبيئة. المبلغ والعملة يمرّان خامَين وتطابقهما `markOrderPaid` بالهللة. لا شيء يُقرأ من رابط العودة، وجسم الإشعار منبّه فقط.
4. كل رفض حادثة في `payment_incidents` وسطر سجل `error` باسم ثابت `payment.incident_open`. **لا تفعيل ولا استرداد آلي.** لا قناة تنبيه للمالك بعد (بريد أو واتساب): سؤال مفتوح، ولوحة الحوادث في المرحلة 5.
5. و6. التحقق من الجوال برمز وجدولة `orders:expire` **لم يُبنيا**، ويبقيان مانعين.

**مزوّد الاختبار (`PAYMENTS_PROVIDER=fake`):** محاكاة في ذاكرة عملية الموقع، بلا شبكة ولا مال. ثلاثة سدود: الإقلاع يرفضه إلا مع `SITE_URL` على عنوان الجهاز نفسه، والبناء الإنتاجي يلزمه أيضًا `PAYMENTS_ALLOW_FAKE=yes`، وصفحته وإجراؤها يردّان 404 لأي طلب ترويسة Host فيه ليست عنوان الجهاز. صفحتها `/checkout/demo-pay/…` معنونة «صفحة دفع تجريبية»، وصفحة الطلب تعرض لافتة «وضع تجريبي». للاختبارات الآلية وللعرض المحلي لا غير.

**ما لم يُبنَ عمدًا:** الاسترداد (قرار مالك)، Tabby وTamara (المنفذ يتسع لهما، 4ب)، الدفع الحي، جدولا `provider_events` و`payment_transactions` (القرار 52)، Moyasar Form وApple Pay على صفحاتنا.

### متغيرات البيئة (أسماء فقط)

| المتغير                        | الغرض                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `PAYMENTS_MODE`                | `off` (الافتراضي) أو `test`. `live` مرفوض                                                                           |
| `PAYMENTS_PROVIDER`            | `moyasar` أو `fake`                                                                                                 |
| `PAYMENTS_MIN_PAYMENT_MINUTES` | أقل وقت لإكمال الدفع بالدقائق. **بلا قيمة افتراضية**: تُقاس في WP0                                                  |
| `MOYASAR_SECRET_KEY`           | المفتاح السري التجريبي (`sk_test_…`)                                                                                |
| `MOYASAR_WEBHOOK_SECRET`       | السر المكتوب في Secret Token برابط الإشعار (32 محرفًا على الأقل، ولا يساوي المفتاح)                                 |
| `MOYASAR_HOSTED_PAGE_ORIGIN`   | أصل صفحة الدفع المستضافة (`https://host`) يضاف إلى `form-action` في CSP مع Moyasar فقط. **بلا قيمة افتراضية** (WP0) |
| `PAYMENTS_PUBLIC_SANDBOX`      | `yes` إذن صريح لفتح الشراء على معاينة عامة بمفاتيح التجربة. **ينتظر موافقة المالك** (القرار 54)                     |
| `PAYMENTS_ALLOW_FAKE`          | `yes` إذن صريح لمزوّد الاختبار على بناء إنتاجي محلي (اختبارات المتصفح). لا يُضبط على خادم                           |
| `PAYMENTS_FAKE_WEBHOOK_SECRET` | سر إشعار المحاكاة المحلية فقط                                                                                       |

الأخطاء عند الإقلاع تذكر اسم المتغير لا قيمته. بلا `PAYMENTS_MODE` لا زر دفع ولا رابط إشعار (404)، والموقع كما كان.

## 10. ربط Moyasar لاحقًا، خطوة خطوة

**قبل أي خطوة:** تُجرى تجربة WP0 (القسم 11) بمفاتيح التجربة ويُحدَّث المحوّل من نتائجها. لا يُفتح الشراء للعموم بهذه الخطوات: هي لمعاينة غير مفهرسة وبيئة تجريبية فقط.

1. **المالك:** ينشئ حساب Moyasar ويأخذ مفتاحي التجربة من اللوحة. المفتاح السري يُعرض مرة واحدة.
2. **على الخادم مباشرة** (طرفية Hostinger، لا المحادثة ولا git): يولَّد سر الإشعار بـ`openssl rand -hex 32`، ثم تُضاف إلى `/opt/masar/deploy/.env` (صلاحية 600) الأسطر: `PAYMENTS_MODE=test`، `PAYMENTS_PROVIDER=moyasar`، `PAYMENTS_MIN_PAYMENT_MINUTES=<قيمة WP0>`، `MOYASAR_SECRET_KEY=<المفتاح>`، `MOYASAR_WEBHOOK_SECRET=<السر المولَّد>`، `MOYASAR_HOSTED_PAGE_ORIGIN=<أصل صفحة الفاتورة من WP0>`، و`CHECKOUT_ENABLED=true`، و**بعد موافقة المالك على القرار 54 فقط** `PAYMENTS_PUBLIC_SANDBOX=yes`. `compose.yml` يمررها إلى الحاوية بأسمائها.
3. يُعاد تشغيل الحزمة. إن كان الإعداد ناقصًا أو المفتاح حيًّا يفشل الإقلاع برسالة تسمّي المتغير. الشراء على الرابط العام مرفوض افتراضيًا، ويُقبل فقط مع `PAYMENTS_PUBLIC_SANDBOX=yes` و`SITE_INDEXABLE=false` (القرار 54 ومخاطره).
4. **في لوحة Moyasar** (Webhooks): رابط الإشعار `https://<نطاق المعاينة>/api/payments/webhooks/moyasar`، والطريقة POST، وSecret Token هو السر المولَّد نفسه، والأحداث `payment_*`.
5. إن ظهر الرابط Unverified: Moyasar يرسل حدث `webhook_verification` برمز من 6 أرقام صالح 30 دقيقة. **نقطتنا توثّقه وترد 200 لكنها لا تحفظ الرمز بعد** (القسم 11، البند 9)، فيلزم إكمال هذا البند قبل هذه الخطوة.
6. تُضبط سياسات النادي المحجوبة في القاعدة (مهلة الطلب وقاعدة البدء) بقرار المالك، وإلا لا يُنشأ أي طلب. المهلة يجب ألا تقل عن `PAYMENTS_MIN_PAYMENT_MINUTES + 5`.
7. تُجدوَل المهمتان على الخادم (مؤقت systemd): `pnpm --filter @masar/db orders:expire` و`pnpm --filter @masar/payments payments:reconcile` (المقترح كل دقيقتين).
8. تُنفَّذ الحالات الخمس عشرة (القسم 5) في البيئة التجريبية ببطاقات الاختبار، ويُسجَّل دليلها في `PROGRESS.md`.
9. **الدفع الحي** خارج هذه الخطوات: إذن مستقل من المالك، وإضافة عنوان IP الخادم إلى Allowed IPs، ورفع رفض `live` بإيداع مراجَع، وبعد الموانع كلها (`PROGRESS.md`).

## 11. ما ينتظر تجربة البيئة التجريبية (WP0)

كل بند `[unknown]` في الوثائق عُزل في الكود بالاتجاه الآمن، ولا يُخمَّن:

| #   | المجهول                                                                                                        | ما يفعله الكود الآن                                                                                                               | أين                              |
| --- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 1   | البحث عن فاتورة يتيمة بـ`metadata[attempt_id]` (شكل رد List Invoices)                                          | خطأ صريح `needs_sandbox_verification` (`moyasar.list_invoices_by_metadata`)، والمطابقة تتخطى الخطوة بتحذير. اليتيمة تنتهي بموعدها | `moyasar/unverified.ts`          |
| 2   | أقل وقت معقول للدفع (3DS ورمز التحقق)                                                                          | متغير بلا قيمة افتراضية `PAYMENTS_MIN_PAYMENT_MINUTES`                                                                            | `config.ts`                      |
| 3   | معنى حالات الفاتورة `paid` و`failed` و`refunded` و`on_hold` و`voided` لقبول دفع جديد                           | `indeterminate`: لا تُنهى بها المحاولة، والحسم بدفعاتها                                                                           | `moyasar/map.ts`                 |
| 4   | حالات الدفعة `captured` و`verified` و`expired` داخل فاتورة                                                     | `indeterminate`: لا تُعامل مدفوعة                                                                                                 | `moyasar/map.ts`                 |
| 5   | مصير دفعة دخلت 3DS قبل `expired_at`، ومهلة `initiated`                                                         | المحاولة تبقى حيّة وتحمي طلبها، وحادثة `stuck_pending` بعد ساعة من موعدها                                                         | `verify.ts`، `timing.ts`         |
| 6   | توثيق `callback_url` للفاتورة                                                                                  | لا يُرسل أصلًا. الاعتماد على الإشعار العام والعودة والمطابقة                                                                      | `moyasar/adapter.ts`             |
| 7   | هل تقبل الفاتورة `apply_coupon`، وهل تؤثر الكوبونات على دفعاتها                                                | لا يُرسل. مفاتيح `#coupon_*` في الدفعة تفتح حادثة، وفرق المبلغ يمنع التفعيل                                                       | `moyasar/parse.ts`               |
| 8   | مفتاح عدم تكرار لإنشاء الفاتورة                                                                                | لا إعادة للإنشاء: الانقطاع يكتب المحاولة `failed`                                                                                 | `start.ts`                       |
| 9   | استلام رمز `webhook_verification` (الحقل `data.verification_code` موثق، ومكان حفظه `provider_events` المؤجَّل) | يوثَّق الحدث ويُرد 200 بسطر تحذير بلا الرمز. **الرمز لا يُحفظ**                                                                   | `web/server/payments/webhook.ts` |
| 10  | هل يحمل إشعار دفعة الفاتورة `invoice_id`                                                                       | إن غاب تُقرأ الدفعة من المزوّد لمعرفة فاتورتها                                                                                    | `notify.ts`                      |
| 11  | حقل بيئة في كائن الفاتورة أو الدفعة، وحصر القراءة بحسابنا                                                      | البيئة من بادئة المفتاح، ويُشترط `metadata.attempt_id` ومعرّف الفاتورة                                                            | `moyasar/adapter.ts`             |
| 12  | طرق الدفع في صفحة الفاتورة (مدى؟ Apple Pay؟)، ودقة `expired_at`                                                | لا نص يسمّي وسيلة دفع. يُرسل طابع ISO كامل                                                                                        | القاموس، المحوّل                 |
| 13  | نطاق صفحة الدفع المستضافة (لسياسة `form-action` بلا JavaScript)                                                | يُشترط `https`. مع JavaScript التوجيه يعمل؛ بلاه قد يحجبه `form-action 'self'` حتى يُضاف النطاق                                   | `config/csp.ts`                  |
| 14  | عناوين IP للإشعارات، ومعنى `payment_abandoned`                                                                 | لا تصفية بالعنوان، وكل حدث `payment_*` منبّه يُقرأ بعده المزوّد                                                                   | `moyasar/webhook.ts`             |

**ثوابت تقنية مقترحة تنتظر مراجعة المعماري** (سؤال 13 في التصميم، `packages/payments/src/timing.ts`): هامش الجلسة 5 دقائق، مهلة استدعاء المزوّد 10 ثوانٍ، عتبة `stuck_pending` ساعة، فاصل المطابقة من دقيقتين إلى 30 دقيقة، وإعادة فحص المسوّاة يوميًا لأسبوع.

حمولات الاختبار الحالية (`moyasar/fixtures.ts`) بشكل أمثلة الوثائق، لا تسجيلات حقيقية: تُستبدل بحمولات WP0 المنقّحة.
